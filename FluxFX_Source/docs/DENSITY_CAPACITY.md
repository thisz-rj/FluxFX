# P1.8 independent density capacity — 0.41.0

The previous adaptive baseline copied the entire main allocation whenever new
bricks appeared. This version leaves global pressure, velocity, hierarchy and
topology metadata in place. Density's two scalar fields occupy a separate
Metal buffer. Its brick capacity doubles until sufficient, capped at the total
domain brick count. Dispatch still covers only active density cells, not spare
capacity. Brick IDs remain append-only.

When expansion fits, the existing allocation is reused with no copy. Otherwise,
a cleared replacement scalar buffer receives only the old active density prefix
through a GPU copy, verified byte-for-byte before swapping. Scratch values are
regenerated by injection. Unused scalar capacity starts at zero and remains
untouched until activated. Pressure/velocity buffers never move during growth.
The 0.40 algorithm remains callable as a diagnostic comparison.

## Results

Tested on M5 Pro / Metal with graphical Blender 5.3.0 Alpha `b2e052b7172a`,
Python 3.13.13. All 237 checks pass: independent 32³ NumPy reference, dense
comparison at 64³/128³, 8³/16³ layouts, five velocity seeds, three source
schedules and horizons through 16 steps. Native tolerance is 1e-6, CPU 1e-4,
and mass agreement 1e-5. The eight-step benchmark measured zero difference in
density, velocity, pressure and divergence. Capacity coverage, copy avoidance,
reuse, preservation, invalid input and owned-buffer cleanup are checked.

A 128³ comparison now succeeds within a 120 MiB per-engine budget; that budget
rejected growth in 0.40. A separate 32³ case deliberately allows initial engines
but rejects a scalar replacement that would exceed peak budget, and confirms
cleanup. Budget enforcement includes the hierarchy and simultaneous old/new
scalar buffers. Geometric growth is rejected if it exceeds budget; there is no
exact-fit fallback. Host vectors and driver allocations are excluded.

Three paired samples follow one warmup per brick size; each run uses eight
steps and eight V-cycles per step. Capacity precedes legacy in every pair, so
order/thermal bias is possible. These are bounded diagnostic timings, not FPS.
The paired native dense reference takes about 297–299 ms wall time and owns
100.948 MiB. Capacity growth removes the large memory spike and reduces elapsed
time relative to 0.40, but still has no overall speed advantage over dense.
Final capacity allocation is slightly larger than exact-fit 0.40 allocation
because it reserves spare cells.

For 8³ bricks, 91 final active density bricks fit in capacity 128. Only 114,688
old density bytes are copied across the two reallocations. Growth copies zero
global-field bytes, versus 675,414,016 in the legacy eight-step run. The full-grid
support scan and synchronization are unchanged. Density allocation remains
separate from smoke occupancy; no 256³ / 8% occupancy benchmark is claimed.

Completed wall timing includes preflight, waits, topology updates, growth,
zeroing, verification and physics, excluding initial setup and final readback.
GPU timing includes detection/copy/physics commands but excludes host work.
Peak owned memory includes hierarchy and temporary scalar replacement. The
comparison holds a separate dense engine, so paired peak is this peak plus
dense bytes. Reports retain `sparse_bytes`/`peak_sparse_bytes` for compatibility;
new `density_capacity`, `density_reallocations`, `density_reuses` and
`global_copy_bytes` make the allocation behavior explicit. Capacity is measured
in bricks; `density_bricks` is the active count. `density_bytes` includes spare
capacity and density topology metadata.

Regression checks pass: adaptive 231, fixed hybrid 209, global coverage 115,
coupled 113, multigrid 171, projection 154, MAC 96, transport 55, regions 24,
resources 29, standalone Python 146 and Blender save/load 15. The Blender UI
report and cleanup check pass. [Reports, timings and hashes](validation/native_p18_capacity)
preserve the tested evidence.

## Run

Build with `python3 scripts/build_native.py` using Xcode on Apple Silicon, then
package with `python3 scripts/package.py`. Install `fluxfx-0.41.0.zip` in
Blender 5.3 and restart Blender when replacing a loaded native binary.
**Native core · P1.8 → Compare Density Capacity** writes
**FluxFX Density Capacity.json** in the Text Editor. Interactive preview remains
the established dense engine.

The Python API is `fluxfx.native.compare_capacity_coupled`. Run
`scripts/capacity_validate.py`, `scripts/capacity_ui_validate.py` (registered
addon) and `scripts/capacity_timing.py` from graphical Blender with the repository
on Python's import path. Reports go into `test-results`. GPU validation still
requires graphical Blender here; no new Blender API limitation was encountered.
