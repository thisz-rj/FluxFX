# P0.9 — M5 Pro benchmarks and bottlenecks

Measured September 21, 2026, Apple M5 Pro / Metal, Blender 5.3.0 Alpha
b2e052b7172a, macOS 27 arm64. P0.9 adds benchmark tooling and evidence; it does
not claim a faster solver. The initial P0.0–P0.9 dense prototype is now implemented.

## Results

| Adaptive simulation, synchronized wall | 4.933 / 5.554 | 75.502 / 269.607 |
| Solver CPU submission, fixed | 0.182 / — | 0.615 / — |

A cold pressure step measured 19.04 ms at 64³ and 268.58 ms at 128³ in the fixed
run. Cold adaptive steps measured 12.04 / 268.26 ms. These are single observations,
not distributions, and can include first-use driver/cache effects.

Adaptive samples include timestep changes that force cold pressure solves:
80/320 iterations at 64³, 320/1280 at 128³. This accounts for a large 128³ tail.
The raw report records per-sample dt and iteration count as well as timing.
Do not interpret these tables as viewport FPS or a realtime guarantee.

## What the measurements imply

Pressure is the largest measured cost, especially at 128³: its isolated snapshot
solve is roughly 65 ms versus 73 ms for a complete fixed step. The isolated case
is not an exact profile of the full step, so this comparison identifies scale,
not an additive attribution of every millisecond. Increasing resolution also
quadruples the pressure iteration budget; this is not just an eightfold increase
in voxel count.

64³ is the practical development starting point on this machine. For 128³,
prioritize a better pressure solver (for example multigrid/preconditioned CG),
then reconsider pressure initialization across dt changes. Do not simply lower
iterations without checking divergence. Adaptive readback adds measurable cost,
but removing it alone would not resolve the 128³ pressure bottleneck. The small
unlit volume inset is comparatively inexpensive in these measurements.

Sparse storage/native code remain possible later steps, but the current evidence
supports improving pressure convergence before expanding the architecture.
These are proposed next steps, not implemented changes in P0.9.

## Methodology and scope

`scripts/benchmark.py` pauses existing playback and creates isolated solver
instances. It does not reset the user's active simulation or change scene
settings. Run it from the Python Console after loading the source add-on.
Blender's main thread is busy during the benchmark; playback remains paused.

Each grid is tested in fixed mode first, then adaptive mode. Both start from
identical default seeds. A separately recorded first step is followed by five
warmup steps and 30 measured steps. Adaptive and fixed trajectories advance by
different simulated times, so the workload is similar but not identical.

A small benchmark-only compute pass consumes all final scalar, velocity, and
divergence fields and writes one texel. Reading that texel synchronizes those
outputs without transferring whole volumes. Synchronized wall measurements
include dispatch and readback overhead. Fence baselines are reported, not
subtracted; subtraction would imply more timing precision than is supported.
CPU submission timings bracket `solver.step` only; adaptive selection is outside
that interval but inside adaptive wall time. This explains why the old submit
readout was much smaller than completed simulation cost.

Pressure-only samples repeatedly project the same velocity snapshot into spare
fields with steady warm-start iterations. Selection-only samples repeatedly
reduce the same final state. These isolate approximate costs without extra
per-pass instrumentation in the real solver.

Render samples draw the current final adaptive density snapshot as a 260×260
pixel inset into a 512×512 RGBA32F offscreen target. The camera is fixed front
orthographic, opacity 3, UI scale 1. Each of 64/128/256 ray samples gets five warmup
renders and 30 measurements. A one-pixel read synchronizes the result. No scene
geometry, viewport overlays, Retina scaling, UI scheduling, display presentation,
lighting, or shadows are included. Performance is specific to this sparse plume
snapshot and view; opaque volumes and other views can change early termination.

This is one session on one machine, not repeated independent trials. Thermal,
power, competing-process, and driver-cache state were not controlled. p95 is a
small-sample descriptive statistic, not a confidence bound. The readback fence
uses normal GPU texture dependency/barrier behaviour; no GPU timestamp API is
assumed. Additional GPU profiler work is needed for precise hardware attribution.

## Reproduce and inspect

In graphical Blender after running `scripts/dev_load.py`:

```python
import runpy
runpy.run_path('/absolute/path/to/fluxfx/scripts/benchmark.py', run_name='__main__')
```

Check `test-results/benchmark.json` has `status: PASS`. It includes device/build
metadata, all timing samples, cold steps, memory, dt/iteration samples, and final
pressure diagnostics. Exceptions leave an incomplete RUNNING report; do not
interpret a partial report as a completed benchmark. Run separately from other
FluxFX validation scripts, which may reload modules or alter the active preview.

- [Raw JSON](validation/m5-pro-benchmark-p09.json)
- [Timing samples CSV](validation/m5-pro-benchmark-p09.csv)

The 53 existing standalone tests still pass. P0.9 changes no numerical kernels;
its added fence shader compiled and ran on Metal for both benchmark grids.
The source archive includes the benchmark runner; both archives include the
fence shader, report, and documentation.
